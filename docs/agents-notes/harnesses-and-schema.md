# Harnesses, provider environment and storage schema

Moved verbatim from `AGENTS.md`, which keeps a short summary of each bullet. Paths and links below are relative to the repository root.

- Harnesses: adding a provider means touching every `"kimi" | "opencode" | "antigravity"`-style match in `providers.rs`/`acp.rs`, the allowlists in `storage.rs`, `overlay.rs`, `architect*.rs`, `terminal.rs`, `slash_commands*.rs`, `provider_settings.rs`, plus `ProviderId` and its `Record` maps on the frontend (tsc flags the maps). ACP harnesses share `acp.rs`; provider quirks (Grok's `authenticate` step, plan-mode policy, `_meta.totalTokens` usage) live behind `config.provider` checks there. Record real frames in the tests, and keep an ignored live smoke test per installed CLI. Key-based Claude Code relays (GLM, MiMo) each get a `providers/<id>.rs` with `environment()/arguments()/configure()/models()`, a `Credential` in `provider_settings.rs` (own secure-store account + env var), and an entry in the `keyed` table of `src/provider-settings.ts`, which renders the card's key form and status. Provider environment variables ([docs/providers.md](../providers.md#environment-variables)): a global set plus per-provider lists in `provider-settings.json` (`provider_settings.rs`; names-only IPC, plain values, connection's `valid_env_name` rules) are merged by `environment()` (global unless the provider opted out, then its own) and applied by `providers::provider_command`/`apply_environment` at every harness spawn — `run_inner`, warm agents (whose key carries `environment_fingerprint`, so an edit starts cold), `terminal.rs`'s harness console, and the catalog/discovery/usage/integrations probes; saving invalidates that provider's usage, catalog and slash-command caches. Cloud runs inherit nothing by default: `cloud_agents/transport.rs::inherited_environment` adds the harness's saved variables only when `cloud::Settings.providers[<cloud>]["inheritEnvironment"] == "true"` (`cloud_set_inherit_environment`, the checkbox in `src/cloud-settings.ts`), refuses loopback proxy values at start, chains them before credentials so credentials win, and mirror tasks on other computers always use that computer's own settings. Schema is at `user_version` 36 (version 36 added machine orchestration in one step: `machine_threads` with `reported_by`, the wake message that reported a thread, `sessions.restart_interrupted`, set when startup interrupts a running task (mirrors keep their status), and `sessions.stop_requested`, the user's Stop saved before the run is signalled so a quit right after it never counts as a restart interruption; version 35 added `task_schedules`, `task_schedule_runs` and `scheduler_settings` for task schedules; version 34 added `task_usage_links`, every harness session id a task has run under, so per-task usage totals can be summed from the agents' own logs; version 33 added `messages.remote_cut`; version 32 `sessions.remote_backfill_base`; version 31 `remote_cursors`; version 30 added `message_attachments`, the images a user message carried: captures copied to `<app data>/attachments/<session>/`, moodboard images linked by id; served to phones by `task.attachment`; version 29 added `bots.skills`/`bots.mcp`, a bot's skill and MCP references, and `bot_tasks`, the bot a project task started with; version 28 added `bots.soul`, a bot's optional personality; version 27 added `sessions.cloud` for cloud agents; version 26 added the mirror columns `sessions.remote_device`, `remote_session` and `remote_synced_id`; the bot tables in `bots::SCHEMA`; version 24 added `sessions.limited_at`, `limited_until` and `resume_at_reset`; version 23 `queued_messages`, the durable per-task queue in `message_queue.rs`; version 22 added `sessions.draft`, set for a New task until its first saved prompt publishes it; version 21 added `sessions.pinned` and `sessions.sidebar_order`, version 20 `sessions.title_origin`, version 19 `sessions.last_prompt_at`). Drafts are excluded from `list_sessions`; empty ones are deleted on leave (`discard_draft`) and at startup. Adding a migration step means bumping `storage::SCHEMA_VERSION` (the outer guard reads it; a test checks it matches the newest `PRAGMA user_version=`) and updating the tests that assert the number.
