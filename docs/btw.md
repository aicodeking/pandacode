# /btw side threads

Type `/btw <question>` at the start of a prompt to ask something on the side while the task keeps working. It works whether the agent is idle or running: the message never joins the task's queue and never steers its run.

- **Where it runs.** A side thread is an ordinary task in the same project, harness, model and checkout, titled `BTW: <question>`. A task in a worktree gets its side thread by forking (`fork_session_at_message`), the only way to share that checkout; the copied transcript stays hidden in the panel. Tasks that run on another computer or a cloud machine, and bot conversations, cannot open side threads. Archived and completed tasks can: ask about finished work without reopening it. Attachments in the prompt are refused for `/btw`; remove them or send without it.
- **The panel.** The inspector's *By the way* tab (view `btw` in `src/inspector-tabs.ts`, opened and selected by `/btw`, closable like any tab; `src/btw-panel.ts`, styles in `src/btw.css`) shows the side thread the way the main pane shows a thread, at panel width. Nothing is re-implemented: `main.ts` hands the panel its own renderers through the panel's host, each parameterized by session: `turnRowsHtml()` (turns, tool groups and traces, coordination and handoff rows, change cards, user messages with attachment chips) with `paintSavedMarkdown()`, `paintStream()` for the live turn (thinking, the step trace and its folding, streaming text, errors and agent questions), and `messageActionsHtml`/`bindMessageActions` for Copy, Fork and Edit. Saved rows redraw only when the messages change, keeping open tools and folds; the live turn redraws once per frame. Each final answer also has *Insert into main*. Header: *New side thread*, *Open as full thread*, *Close*, and a status (*Working*, *Needs your input*, *Ready*, plus *· main running*).
- **The composer.** Built from the main composer's pieces, scoped to the side thread: the model trigger (`modelTriggerHtml()`, the same picker with effort, saved with `configure_session`/`set_reasoning_effort`) and permissions (`modeTriggerHtml()`, `update_session`); `showModel`/`showMode` take the target task, and every composer `data-action` inside `.btw-panel` (model, mode, stop, approvals, queue rows) acts on the side thread through `actionTask()`. Enter sends while the side agent is idle and queues (`queue_add` for the side thread) while it works; ⌘/Ctrl Enter or *Steer* steers it (`steerOrQueue()`, the main composer's steer-then-queue path); *Stop* stops only it. The side thread's approvals (the main approval bar's markup, `taskApprovalsHtml()`) and its queue (`queuePanel`) sit above its prompt; questions show in its live turn. Slash commands and @ mentions mount on the side prompt. App slash commands go through `btwSlash()` in `main.ts`: `/model` and `/permissions` open the panel's own pickers, `/init` and `/recap` send their prompt to the side thread, `/rename <title>` renames it, a short allowlist (`SIDE_SAFE_SLASH`: Codex command panels, `/export`, `/fast`, `/plan` without text, `/settings`, `/theme`) runs for it, and any other app command (one that would act on the open thread, such as `/pwd`, `/diff` or `/copy`) is refused with *Open the side thread as a full thread to use /x*; harness commands go to the side agent as text. `/btw …` typed there just sends to it. The draft is the side thread's own (`state.drafts`). Esc in the panel returns to the main prompt and never stops either agent. Steer is hidden while the side thread runs a team, which takes messages between runs.
- **Before the first message.** With no side thread yet the composer still shows the model, effort and permissions, starting from the main thread's. Picks are kept on a stand-in task per main thread (`btwDraftTask()`/`btwDrafts`) and nothing is saved; `createBtw` applies them to the new side thread (`applyBtwDraft`: `configure_session`, `connection_assign` for a named connection, `set_reasoning_effort`, `update_session`) before its first `send_message`. If one fails, the new task is deleted, the error names the setting, the picks stay and the `/btw` text comes back. The pickers are disabled while a side thread is being created. Named agent teams are not offered there.
- **Out of scope.** The side composer has no attach (+) button: `/btw` refuses attachments, and the main pipeline mixes per-session state (`attachments.ts`) with global composer state (project-file paths, browser and moodboard items), so scoping it needs its own change. The Team and token-saver buttons also stay in the main composer only; open the side thread as a full thread for them.
- **Referencing the main thread.** Every side-thread message, including queued follow-ups (added when `deliverQueued` sends them), carries a `Main thread context:` block (shown as a *Main thread context* chip that opens its raw text, via `src/message-attachments.ts`) built by `mainContext()` in `src/btw.ts`: the main thread's title and status, then its user and agent messages the side thread has not seen yet (the recent tail on the first message), plus its in-progress reply. It is capped at 24 KB, keeps the newest text, and says when older text was left out, including history older than the loaded page.
- **Links.** `localStorage['pandacode.btw']` maps each main task to `{ sideId, seenId, hiddenThrough? }`. Follow-ups reuse the linked side thread; a deleted or archived side thread is not reused (unarchiving it brings it back) and the next `/btw` starts a new one, and deleting the main task removes its link. Concurrent `/btw` sends for one task run one at a time, so they never create two side threads; a send while the side agent still answers is refused (the panel queues instead). The panel comes back with the main thread through the inspector's per-thread state.

Tests: `tests/btw.test.mjs` (parser and context builder) and `tests/btw.spec.ts`.
