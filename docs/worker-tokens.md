# Where a team worker's tokens go

Batch S1v3 ([token saver benchmark](token-saver-benchmark.md)) showed the token saver packs save nothing measurable: output is about 1% of a worker's tokens. This page finds where the rest goes, picks one lever, builds it, and measures it (batch S2).

## Breakdown

Sonnet workers in Claude Code 2.1.317. Dollars use the prices `metrics.mjs` fits to billed costs: cache write $4/M, cache read $0.10/M, output $10/M.

| Batch | Runs | Steps | Billed | First-step write | Later writes | Cache reads | Output |
|---|---:|---:|---:|---:|---:|---:|---:|
| S1v3 | 340 | 4.2 | $0.157 | 25.3k tok, **$0.101** | 6.2k, $0.025 | 144k, $0.014 | 1.7k, $0.017 |
| Fv2 | 240 | 5.4 | $0.144 | 18.5k tok, **$0.074** | 7.7k, $0.031 | 193k, $0.019 | 2.0k, $0.020 |

**Cache writes are 80% of a worker's cost in S1v3 and 73% in Fv2, and the first step's write alone is 64% and 51%.** Cache reads are 81% (S1v3) to 87% (Fv2) of the tokens (reads / (writes + reads + output)) but under 15% of the cost.

### What the first request holds

We captured one real request through a local proxy and probed the pinned harness with different flags (`claude -p "Reply with the single word ok"` in a fresh git folder, first-request usage):

1. **Tools and the static system prompt** come first. Claude Code marks the system prompt with a 1-hour cache breakpoint, so this prefix (10–12.7k tokens with the default tools) is shared by every run on the account. It is a cache **read** every step, not a write.
2. **The first user message** holds the project's memory files (CLAUDE.md, AGENTS.md, user rules), the user context, then the task.
3. **A trailing environment block** holds the working folder, the deferred-tool list, the agent types, the skill listing and the date. Its end carries the only message breakpoint.

There is no breakpoint between the memory and the per-run parts, so **every worker writes the project memory again**, even when every worker in the team has the same files. The PandaCode `AGENTS.md` measured about 38.4 KB on 2026-11-10 (71,970 B in the last release commit). It was 28.7k tokens on the larger copy these runs used, and the token count has not been measured again since it shrank. By repo, S1v3's first-step write on those copies is 34k (PandaCode), 8k (Outline) and 4.5k (VS Code). The memory is the largest single cost, and it is the user's. `AGENTS.md` has since shrunk further (14,471 B), so that remark applies to the larger copy those runs used; the numbers above are unchanged.

| Probe (no project memory, `--setting-sources project`, warm second run) | Tools | Prefix tokens | Written fresh per run |
|---|---:|---:|---:|
| Default tools | 23 | 15.9k | 3.4k |
| App's launch today (`ScheduleWakeup,Monitor,CronCreate` off), S2's BASE | 20 | 14.2k | 3.3k |
| Worker trim, writer | 10 | 9.4k | 2.7k |
| Worker trim, read-only, S2's LEAN | 7 | 8.8k | 2.7k |
| Worker trim, read-only, and `Skill` off | 6 | 5.9k | 0.4k |
| No tools (`--tools ""`) | 0 | 1.8k | 1.8k |

With the user's own settings (here: about 60 installed skills and a SessionStart hook), the trailing block is 37.9k characters, and **the skill listing alone is about 8k tokens written by every worker**. The read-only trim takes the prefix from 28.9k to 23.6k, and also turning `Skill` off takes it to 12.1k.

### Levers tried and dropped

- **Move the memory into the cached system prompt** (`CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` plus `--append-system-prompt`). The appended copy was read from cache by the second run (38.7k read), but 2.1.317 still loads AGENTS.md through its built-in `cc-plugin-agents-md` plugin, so the memory was sent twice. Rebuilding Claude Code's memory discovery (ancestors, `.claude/rules`, imports, CLAUDE.local.md, AGENTS.md) by hand would risk dropping user rules without anyone noticing. Not safe.
- **A primer session forked by each worker** (`--resume <primer> --fork-session`). The worker's own request did read the memory from cache (39.5k read, 3.4k written), but a resumed session makes a second hidden request that writes the whole prefix again. Its billed cost was $0.149 against $0.132 cold. Dead on this harness.
- **`--exclude-dynamic-system-prompt-sections`**: no change. The environment is already a trailing block.
- **Shorter brief or smaller app instructions**: the app instructions sit in the system prompt, so they are cached reads. A worker's brief is under 1k tokens of the first write.
- **Output packs**: S1v3 showed output is about 1% of tokens and 11% of cost.

## Decision

**Team workers launch without the Claude Code tools their brief already forbids.** That is native subagents and workflows, other sessions, worktrees and cloud routines: `Agent,Task,Workflow,ListAgents,SendMessage,RemoteTrigger,CronDelete,CronList,EnterWorktree,ExitWorktree`. Read-only workers also lose `Edit,Write`; `NotebookEdit` stays listed from the first turn and is refused while read-only. `TaskStop` stays: it also stops a worker's own background Bash.

Seven of these are tools Claude Code defers: `NotebookEdit`, `SendMessage`, `RemoteTrigger`, `CronDelete`, `CronList`, `EnterWorktree` and `ExitWorktree` (`CLAUDE_DEFERRED_TOOLS`).

- History can hold a ToolSearch reference to one, and removing its definition breaks later requests.
- A new conversation removes denied deferred tools except `NotebookEdit`, whose definition stays listed so a read-only worker can later become a writer. A resumed launch keeps what its conversation held; unknown history keeps all seven (`History::lists_native`).
- A kept tool the role denies is refused by a `PreToolUse` hook registered at `initialize`, in every permission mode (`claude_refusal_hooks`), because `can_use_tool` is not consulted in Full access, nor for edits in Accept edits. Fresh read-only workers register this hook for `NotebookEdit` too; `can_use_tool` also refuses it whenever consulted.
- The tests in `providers.rs` use frames recorded from Claude Code 2.1.322 (the `initialize` hooks payload, the `hook_callback` and the deny reply; `the_refusal_hook_matches_frames_recorded_from_claude_code`). They were captured with `-p`, stream-json and `bypassPermissions` against a loopback model stub with a fake key, so no real API call was made.
- In that run the CLI accepted the hooks and refused `NotebookEdit` without running it. This covers one CLI version over loopback; it was not a subscription-login run.

The deferred-tool list stays fixed, since adding a deferred tool changes the request. New read-only conversations keep `NotebookEdit` defined and record it in the catalog, so promoting a worker restores `Edit`, `Write` and `NotebookEdit` with trim on or off (`promoted_read_only_workers_regain_all_edit_tools_without_changing_deferred_definitions`). Turning read-only again keeps the notebook definition and restores the refusal. Older conversations that started without a deferred definition still keep it absent. The deny set is computed once per launch and is part of the warm key, so a spare started with a different set is never adopted.

It changes nothing a worker is allowed to do. The brief says "Do not spawn native subagents", workers share one checkout, and read-only workers are told not to edit. It saves about 5.4k cached tokens on every step and about 0.6k of the first write. S2 measured billed cost at -1.8% (CI -4.4% to +1.0%, p = 0.30), so a cost saving is **not shown**: the removed tools were cache reads.

**Worker quality under the trim is not measured end to end.** S2 and S3 ran only localization and report tasks, so S3's writer units were those same tasks under a writer's launch, not real edits. Launch benchmark G2 emulates CLI launches (GUI, approval and queue behaviour are outside its scope) and has 0 of 480 main runs so far, blocked by account quota ([gui-benchmark.md](gui-benchmark.md)). S2's quality figures are descriptive with no gate, and steps rose 6.9% there (also descriptive).

**The trim is opt-in (Settings → Agents → Trim worker tools, off by default; `worker-trim-on` marker, unreadable means off) because it has no measured token saving.** S2 found no billed-cost saving (−1.8%, CI −4.4% to +1.0%, spanning 0), steps rose 6.9% (CI +0.7% to +14.0%), LEAN workers made 92 Bash calls against BASE's 51, and writer quality is unmeasured (G2: 0 of 480 main runs). With `Skill` on (the default), what the trim buys is a smaller, stable cached prefix and a slightly faster start, not measured money. The bigger S3 saving applies only when the user turns `Skill` off and has a real skills library.

**`Skill` is on for workers by default.** Settings → Agents → Workers can use skills decides it (on; the `worker-skills-off` marker in app data turns it off).

- While it is off, team workers on Claude-family harnesses (Claude Code, GLM, MiMo and Alibaba Token Plan) get `Skill` denied. Leads and ordinary tasks always keep `Skill`.
- The worker rules' "no Skill tool" sentence appears only while it is off and only for harnesses that really deny `Skill` (the Claude family). A user rule telling workers to use a skill stops working only then.
- None of 1,573 real worker transcripts on this machine called `Skill`. Its listing is about 8k cache-write tokens per worker with a real skills library.
- **`Skill`'s own effect on billed cost was not isolated.** Batch S3 compared the worker launch that denies `Skill` with the launch before it on a copy of a real skills library. Its arms differ in three things: the `--disallowedTools` list (`Skill` added, `TaskStop` removed), the MCP server (BASE also lists the agent-made tools) and the instructions (BASE also has `REUSE`).
- That whole bundle came to about $0.037 less per worker run, a −20.5% ratio of means, 91% of it ($0.034) the first-step cache write ([worker-tokens-benchmark.md](worker-tokens-benchmark.md#batch-s3-results)). That write's drop is about 19% of BASE's $0.181 mean bill but only about 5% of its tokens (8,465 of 165k).
- There is no measured saving without such a library: batch S3b, which tested only the bundled skills, was voided by a usage limit after 32 of 336 runs and has no result, so the −20.5% applies only to a real skills library.
- Worker quality with or without `Skill` is unmeasured ([architect-workers.md](architect-workers.md#execution)).

- Code: `providers::claude_disallowed_tools`, the `CLAUDE_*_DENIED_TOOLS` constants and `CLAUDE_SKILL_TOOL`.
- `architect::worker_trim` sets `RunConfig::worker` (`WorkerTrim { read_only, skills, trim }`, `None` for a lead or plain task) when the turn is prepared. The launch fills `skills` from `architect::worker_skills_on` (the `worker-skills-off` marker in app data; an unreadable setting stays on) and `trim` from `architect::worker_trim_on`. With `trim` off workers get the plain tool set; read-only enforcement and the Skill switch apply either way.
- The trim and the deny set computed from it once per launch are part of the warm key (`warm::key_with`), so a changed trim starts cold.
- Tests: `providers::tests::workers_launch_without_the_tools_their_brief_forbids`, `warm::tests::a_worker_trim_change_starts_the_next_turn_cold`, `architect::tests::only_team_workers_get_a_tool_trim_and_read_only_ones_lose_edits`, and `tests/worker-skills-setting.spec.ts`.
- Leads, ordinary tasks, and Bash, Read, ToolSearch, WebFetch and WebSearch are unchanged.
- Managed team workers are not offered agent-made tools (`custom_tools`) or the `REUSE` instruction: no real transcript saved or ran one.

### PandaCode's own tools and instructions for workers

- `Role` in `src-tauri/src/app_instructions.rs` (`Task`, `Worker`, `ReadOnlyWorker`; `Role::wants()` → `HostTrim`) decides which PandaCode tool families a turn wants; `src-tauri/src/app_instructions/catalog.rs` (`History`, `Layers`) decides which it lists.
- It is recomputed on every turn from the worker's current assignment (`architect::worker_trim`), so a lead's follow-up that flips `readOnly` changes that turn's instructions and, on a new conversation, its catalog.
- On a harness without a system prompt, a resumed worker hears the short worker instructions again only when its role differs from the one they last went out for (`instructions_due`, recorded by `instructed_as` once a turn carrying them succeeds), or on a reminder turn.
- Leads and plain tasks keep every family.
- The trim (`RunConfig::worker`) and the tool catalog are both part of the warm key (`warm::key_with`), so a changed trim or catalog never adopts a process started with the old one. Today workers are not prewarmed at all (`warm_next` skips managed workers).

- **Every managed worker** does not want `pandacode_title` (workers never get a title run), the four `pandacode_schedule_*`/`list_schedules`/`cancel_schedule` tools, or agent-made tools.
- **Read-only workers** also do not want `pandacode_progress_snapshot`, `pandacode_design_write`/`design_resolve`, or `pandacode_track_files` and its instruction. They keep `pandacode_design_list`/`design_comments`, `pandacode_preview_file` and `pandacode_run_project`, which reviewers read with. Their tracker still runs on native write events. The tracking instruction follows the current role on every harness.
- **Only a new conversation should drop an unwanted family.**
  - The intended invariant for every tool trim is list-and-refuse: a resumed conversation should not lose a tool definition it may already hold (Claude can keep a ToolSearch `tool_reference` in resumed history, and removing the definition breaks later requests).
  - For PandaCode's own families, `Layers` keeps any unwanted family the conversation may hold listed, and every call to it is refused (`refuse_tools`).
  - Agent-made tool names (list, save, run) that a turn leaves out but a resumed conversation may hold stay listed with their real definitions and are refused the same way (`Layers::hold`).
  - A Plan turn, new or resumed, also lists whatever a Standard turn would, in the same position and refusing what Plan does not offer, so Plan-then-implement never changes the list (`plan_mode_lists_the_same_spec_bytes_in_the_same_order_as_standard`).
  - What a conversation may hold is remembered per task (`catalog::remember`, persisted in app data's `session-state.json` by `src-tauri/src/session_state.rs`): the tool names its turns listed on that conversation.
  - A task with no record (never seen, evicted past the 400-task cap, or a missing, corrupt, over-8 MiB or other-version file) has unknown history, and every family a layer can add is kept.
  - Codex sends dynamic tools only when its thread starts, so a family that can become wanted later in the same conversation (a read-only worker's writes, `flips`) is listed from a Codex thread's first turn and refused while read-only. A read-only Codex worker therefore saves none of the write definitions.
  - Tests: the 13 in `app_instructions/catalog.rs` (`a_resumed_worker_that_listed_titles_keeps_them_listed_and_refused`, `codex_lists_a_family_that_can_flip_from_its_threads_first_turn`, …).
- **Per-conversation state survives a restart.**
  - The role its instructions last went out for, how far its compactions were read and answered, the tool names it may hold and its Project tools note counter live in app data's `session-state.json`.
  - `session_state.rs` keeps one JSON file, rewritten atomically by temp file and rename when an entry changes. It holds at most 400 tasks, evicted by last use. Files over 8 MiB, corrupt, missing or of another version read as empty.
  - An empty record behaves as a fresh process did: unknown history keeps every family listed and the instructions and note go out again.
  - Tasks deleted by paths that do not clear their entry (bot resets) are pruned at startup (`session_state::retain` in `lib.rs`).
  - A resumed turn after a restart therefore lists and says what the same process would have, and sends the same except for lazily written marks (the note counter, compaction scan positions): one not yet saved at the restart resends its short text once (`a_restart_lists_exactly_what_the_same_process_would`). After a crash (no exit flush) a task keeps its older saved values rather than reading as unknown.
- **A read-only → writer flip rewrites the cache once.** `pandacode_track_files` is always loaded on Claude (never deferred) and the tracking instruction is part of the system prompt, so the first writer turn of a conversation that was read-only changes both the tools prefix and the system prompt; later turns read the new prefix from cache.
- **Native slash-command turns run bare** (`app_instructions::bare_command`): when the message is a slash command the harness runs itself (Claude Code and Codex pass everything after the name as `$ARGUMENTS`), it carries no tracking, Plan or Project tools note and no message-borne instructions. Nothing skipped is recorded as sent, so it rides the next ordinary turn; a harness without a system prompt that starts a new conversation with a command (Codex) owes that conversation's instructions to its next message (`slash_command_turns_carry_no_message_notes_and_owe_a_new_conversations_instructions`).
- **"Accepted" marks need a whole successful turn.**
  - The records that the instructions went out for a role (`instructed_as`), that a compaction was answered (`compaction_answered`) and that the Project tools note was sent (`NoteMark::accepted`) are written only when the whole turn succeeds and is not stopped (`result.is_ok() && !was_stopped` in `lib.rs`), not when the harness takes the launch.
  - "Accepted" means the turn ended cleanly. A stopped turn therefore resends that text once on the next turn.
  - A team brief's mark follows the same rule (`coordination::brief_accepted`, `brief_refused`).
  - Team rules and mailbox messages a turn delivered are likewise marked delivered only when the run ends cleanly, so a failed or stopped turn sees them again.
- **How `session-state.json` is written (intended behaviour).**
  - Hot-path counters and marks (the Project tools note counter, compaction scan positions and similar) are saved lazily, since losing one only resends a short text.
  - A widened tool listing is saved conservatively, before it matters, because forgetting a tool a conversation holds would break it.
  - If a listing save (`update_now`) fails, that task's listing is dropped in memory and on disk and reads as unknown history, which keeps every family listed; its other fields stay. A background write that finishes after the failure cannot bring back an older, narrower listing.
  - A failed lazy save is retried once, then waits for the next change or the exit flush (which also finishes a background write still in progress).
  - A listing recorded before the harness reported a conversation id applies only until a concrete id is seen; after that the record follows the real conversation.
- **Refused tools never ask on Claude.** On Claude-family harnesses a tool listed only to be refused is auto-allowed at Claude's own permission layer (`Protocol::refused_tools` in the `can_use_tool` handling in `providers.rs`, filled from `RunTools::refused`, the host's real refused set), so the handler refuses the call without an approval prompt. Codex and ACP harnesses have their own permission layers, which may still prompt for a refused tool before PandaCode's handler refuses it.
- **Change tracking instruction** is one text in every mode and harness (`turn_changes::instruction()`, 625 B, the constant's length): every edit batch, native tools included, begins a capture first.
  - It is part of the cached app instructions, so it never depends on the run's mode, allow rules or connection (a different prefix would make the harness rewrite the whole history's cache).
  - Only when native edits wait for approval does the turn's own message carry a 160 B note (`turn_changes::host::turn_note`, `EDITS_NOTE`; the test asserts < 200 B). It says native edits are tracked automatically from their `write_paths` events, so `begin`/`complete` are needed only around shell commands and scripts that edit files.
  - Edits wait for approval (`edits_wait_for_run`) for Claude, GLM, MiMo and Alibaba Token Plan in Standard mode (`edits_wait_for_approval`), and for Claude only with no user allow rule for `Edit`/`Write`/`NotebookEdit` in the Claude settings files. The allow check reads the user config folder, every project folder from `cwd` up to the repository root and, in a linked worktree, the main checkout's `.claude/settings.local.json`, resolved by the shared `resolve_claude_config_dir_env` and `project_config_roots` helpers in `src-tauri/src/claude_roots.rs` (a top-level module beside `account_config.rs`, declared in `lib.rs`). `claude_restricts_reads` (the explorer's read-rule check) resolves folders from the merged launch environment — the saved provider environment plus the named connection's variables (including `HOME`/`USERPROFILE` and `CLAUDE_CONFIG_DIR`), in `Launch::apply` order; the warm key uses the same order over non-secret variables without reading the secret store. A named connection, an unreadable config or any host managed policy counts as allowing (fails closed), present or unreadable: on macOS `/Library/Application Support/ClaudeCode/managed-settings.json` and `managed-settings.d`; on Linux `/etc/claude-code/managed-settings.json` and `managed-settings.d`; on Windows `managed-settings.json` and `managed-settings.d` under `C:\Program Files\ClaudeCode`, `%ProgramFiles%\ClaudeCode` and legacy `%PROGRAMDATA%\ClaudeCode`, plus the `HKLM` and `HKCU\SOFTWARE\Policies\ClaudeCode` registry keys.
  - Switching modes therefore never rewrites the cache (`instruction_is_one_wording_and_only_waiting_turns_get_the_note`).
  - The agent-made tools sentence is one fixed text (`REUSE`), said whenever the run is offered the tools, in every mode. Whether the project has a tool rides only the per-message Project tools note (`none saved yet` when empty), and the tool specs are the same either way, so a first save or last removal changes neither the cached text nor the warm key.
  - The choice is persisted per task (`session-state.json`), so a restart keeps it; only a task with no record picks again.
  - Plan's caveat that tools cannot be saved or run is a 63 B line on the turn's message (`plan_tools_note`).
  - A native write whose baseline already equals its result still marks the turn partial ("Unreported or ambiguous edits were omitted") rather than showing no change (`turn_changes::host::tests::a_native_baseline_that_lost_the_race_is_flagged_never_silently_clean`).
- **Harnesses without a system prompt** get `RICH_QUESTIONS` and `GENERATIVE_UI` once per conversation.
  - On their every-8th reminder turn a self-contained one-line `RICH_REMINDER` (330 B, the constant's length) takes their place (`periodic_instructions`).
  - It names the blocks itself (```ui, ```chart, ```svg, static ```html, workspace images) instead of pointing back at the first message, so it stays true after a compaction the harness did not report: 5,652 → 4,086 B for a project task (`periodic reminder:` line of `cargo test --lib app_instructions -- --nocapture`).
  - A compaction the harness did report resends the full instructions on the next turn (`new_compaction`, recorded by `compaction_answered` once that turn succeeds; the record is persisted per task, so a restart does not resend them).
- **Compaction detection** reads the stored rows: a reported compaction is saved as a flat `tool_activity` row named `Compact context` (`COMPACT_CONTEXT_TOOL`), matched by the row's own name and output, never by text an agent printed. `app_instructions::new_compaction` is covered end to end, from a real Claude `compact_boundary` frame through storage (`a_claude_compact_boundary_stored_like_a_run_is_found_as_a_compaction`). `architect::coordination::compacted` runs the same match but is covered only through stored rows, not from a real `Protocol` frame.

Bytes per request (tool JSON, compact; tokens at ~4 B/token are (est.)). The instruction texts are the constants' lengths. The per-family catalog sizes (title 406, track 696, schedules 4,130, progress 2,282) were measured by serializing the tool JSON: title is the raw tool JSON, 406 B (`serde_json::to_string(&host.tools[0])`; `title tool: JSON 406 B, GUIDANCE 558 B` from `cargo test --lib session_titles -- --nocapture`). The other families are not asserted by a test, so they are (est.):

| Managed read-only worker, new non-Codex conversation | Before | After | Saved |
|---|---:|---:|---:|
| Change-tracking instruction | 625 B | 0 | 625 B |
| Tool catalog, dropped families only: title 406, track 696, schedules 4,130 (when Settings lets agents schedule), progress 2,282 (local runs), design write/resolve (part of the four design tools' 1,095 B) | 7,514 B (406 + 696 + 4,130 + 2,282) + design write/resolve, under 8,609 B (7,514 + 1,095) (est.) | 0 | **full-schema bytes, upper bound** (see below) |

- The catalog row counts only the families a read-only worker drops; design list/comments, `preview_file` and `run_project` stay listed and are not in it.
- It is what a harness that receives full tool schemas on every request saves: under about 2.2k tokens (est.) (8,609 ÷ 4 ≈ 2,152) per request.
- **For Claude-family workers it is an upper bound**: Claude Code defers MCP tool schemas and lists only their names until `ToolSearch` loads one, so the per-request gain there is a few dozen bytes per dropped tool name (est.), plus the 625 B instruction.
- The exception is `pandacode_track_files`: it is always loaded on Claude (`anthropic/alwaysLoad`, `listing` in `providers/mcp_host.rs`), never deferred, so its 696 B (est.) is a real saving there.
- The title tool is now always loaded on Claude too (about +406 B cached per conversation), so a title alongside another call never needs a `ToolSearch` step first, whatever the size of the rest of the catalog. In the one-tool smoke below, Claude Code 2.1.325 did not defer the tool without the flag either, so the step this saves shows only when the full PandaCode catalog is large enough to be deferred (not measured).
- A read-only worker whose conversation may hold the write families (it was a writer earlier in it, its history is unknown, or it runs on Codex) keeps them listed (calls refused), so its catalog saving is only the 4,536 B (est.) of title and schedules (406 + 4,130) that every worker drops on a new conversation.

A writer worker saves 4,536 B (est.) of catalog (title and schedules; again an upper bound on Claude-family harnesses); its tracking instruction is unchanged. These bytes are cache reads after the first step, so the dollar effect is small (see [Batch S2 results](#batch-s2-results)); no paid benchmark was run for this change.

### Team briefs

Checked on the test fixtures in `src-tauri/src/architect/tests.rs` (no paid run; the figures are the `documented_brief_sizes` lines of `cargo test --lib architect::tests -- --nocapture`):

- **Launch briefs** list team notes in full, newest first, within 3,072 B (`LAUNCH_BUDGET`), then previews within 1,024 B (`PREVIEW_BUDGET`), then a count of the rest; `pandacode_team_notes` `get` returns a note's full text, and a note shown only as a preview arrives in full on the next turn unless fetched (`a_launch_brief_lists_full_notes_while_they_fit_then_previews`, `notes_shown_only_as_previews_arrive_in_full_next_turn_unless_fetched`). Measured: 9 notes that fit take 2,901 B; 21 notes take 3,916 B (9 full, 5 previews, 7 counted).
- **Team tool catalogs** are 4,359 B for the architect and 3,170 B for a worker (`team_turn_overhead_stays_within_budget`, which asserts ≤ 4,365 and ≤ 3,175 B). The `tokenSaver` parameter's schema is one line (`token_saver_schema`); its explanation is `saver::LEAD_SAVER_GUIDANCE` in `src-tauri/src/architect/saver.rs`, added to the lead's rules only while token saver packs are on in its thread (or its team guidance mentions them). The dispatch description itself carries none of it; that literal opens with `Start assignments` because the pinned `findLeadGuidance` finds it that way.
- **The lead's full coordination brief** goes out on a fresh conversation, at once after a compaction the harness reported (`a_fresh_or_compacted_context_gets_the_full_brief`), and when the rules change other than the roster (`briefing.rs`, `needs_full`); other turns get a one-line reminder and only unseen messages and notes.
- **A roster-only change** (a model paused, a worker added) is a `Team roster update` delta line instead of the full rules; the test asserts the delta turn is under half the size of the first full brief (`a_roster_change_is_a_delta_line_not_the_full_rules`). Measured: 1,880 B of full rules (2,282 B launch brief) → 518 B delta. The roster is the team's usable model profiles and the routing note that counts them (so a model paused or allowed again by model health changes it); dispatching a worker does not.
- **The periodic refresh** (every 8th turn) resends the rules but not the messages and notes the agent already saw, and adds a compact identity block (the agent's team ID, the never-poll rule, its saved checkpoint and the note keys) so a harness that compacted silently gets its identity back.
  - The block is 457 B (`periodic refresh identity block:` line of `a_periodic_refresh_resends_rules_but_not_messages_or_notes`, asserted < 700 B).
  - The net saving is the bytes of already-seen messages and notes minus those 457 B, so it depends on the mailbox.
  - On the fixture the full brief is 2,424 B, the rules alone 1,783 B, and the refresh with the identity block 2,242 B, a net saving of 182 B; with an empty mailbox and no notes the refresh costs the block instead of saving anything.

## Turn speed: cached instructions and warm spares

- **App instructions** (`app_instructions()` in `src-tauri/src/app_instructions.rs`) assemble sidebar titles, `pandacode-run.sh`, change tracking and `LOOK`.
  - `LOOK` and the other instruction constants live in `src-tauri/src/app_instructions.rs`, where the benchmark scripts read them (`EDIT_CLAUDE` and `EDIT_OTHER` follow `LOOK`).
  - Claude-family harnesses (Claude, GLM, MiMo, Alibaba Token Plan), Pi and Oh My Pi get them once as `--append-system-prompt` (`takes_system_instructions`), which caches with the prefix. Other harnesses get them in the message on a new conversation and every 8th turn.
  - Only a one-line current-title note rides each message. A change to the fixed instructions costs each resumed conversation one cache rewrite.
  - Sizes (local macOS Claude, explore on, agent-made tools off, `cargo test --lib app_instructions -- --nocapture`): lead 6,325 B and writer worker 1,627 B for every Claude-family model. `EDIT_CLAUDE` is 154 B and `EDIT_OTHER` 66 B.
  - A read-only worker is 847 B: it hears no edit sentence and no change-tracking text.
  - The cached lead prompt as a whole is unmeasured: Fv2 measured an earlier Read-first text, not the current edit text or title guidance (Fv2's step results are for Sonnet localization only).
  - **Edit text**: every Claude-family writer (Claude, GLM, MiMo, Alibaba Token Plan, any model) gets one text, `EDIT_CLAUDE` ("Before editing a file, Read the lines you need with Read (explore reads don't count). Make each file's changes in as few edit calls as your editor allows."); other harnesses get `EDIT_OTHER`; a read-only worker gets neither. It does not depend on the model, so the cached bytes are stable. Rule, reasons and evidence: [agent-tools.md](agent-tools.md#instruction).
  - **Titles** (`session_titles::GUIDANCE` 558 B, tool JSON 406 B; `title tool:` line of `cargo test --lib session_titles -- --nocapture`, 964 B together): `GUIDANCE` says when to title (a better title is clear: 3–8 words, topic not status) and carries the whole call rule: alongside another tool call; alone only on a clear topic change or when the title is just the first message. The tool's own description repeats it and adds that a title is set at most once per turn and never overrides a manual name.
  - **Title smoke (2026-11-17, Claude Code 2.1.325, no benchmark):** a stdlib MCP server exposing only the title tool, PandaCode's exact per-message metadata block, `GUIDANCE` appended to the system prompt, and 6 turns per variant in a scratch repo (3 code tasks, 2 chat-only, 1 resumed topic change). Sonnet, HEAD's description and `GUIDANCE` (no `alwaysLoad`) against the current ones: each titled 1 of 6 turns, the topic change, and both calls were alongside a Bash call; neither used `ToolSearch`. Assistant steps were 11 (current) and 12 (HEAD); the current call sent a valid title, HEAD's sent empty arguments, which `suggest` refuses. Haiku titled no turn with either text (0 of 6 each, same setup, HEAD's tool without `alwaysLoad`), so the small model's silence is not new. n=6 per variant, one run each, fake server: it shows the new wording is not worse in that run and costs no solo title step, not that it is better. Provisional titles from the first message (`initial_fallback`) cover turns the agent does not title.
- **Turn end** (`reap`, `await_exit`, `spawn_exit` in `src-tauri/src/providers/exit.rs`): a clean Claude-family turn (Claude, GLM, MiMo, Alibaba Token Plan) ends at `result`, before its CLI process has exited. In-turn steps and tokens are unchanged.
  - **Behaviour**
    - The process exits in the background (`BACKGROUND_EXIT_WAIT` 3 s, then `TERM_WAIT` 0.5 s; inline finishes keep `EXIT_WAIT` 1 s). The natural exits measured below (550–1,917 ms) all fit inside the 3 s, so none of the measured turns was SIGTERMed. Anything that really waits for the exit hurries it: `await_exit` (a cold launch, `quiesce`, merge, the console, deletion) tells the pending reap, which then escalates at `EXIT_WAIT` (1 s) after it began, or at once if that has passed, exactly as before the background reap. A warm spare and a Turn check wait with `await_exit_patiently`, which never hurries, so they get the natural exit up to `BACKGROUND_EXIT_WAIT`. stdin is closed at once, before the reap waits behind any earlier exit of the session, so the CLI never idles with it open; stdout is drained and discarded meanwhile.
    - Managed team workers, cloud runs, and failed or stopped runs finish inline: their process group is gone before the lead reviews or the run reports.
    - A nonzero late exit is logged once to stderr (`exit_note`), but not when PandaCode's own SIGTERM/SIGKILL caused it (a distinct short "was still exiting" line instead): the session id and exit status, plus the last 300 characters of stderr (`NOTE_TAIL`). The relay key, named-connection values and the run's tool-server token are redacted from that tail.
  - **Who gains.** The Done state and PR detection start about 0.8 s sooner on an ordinary turn (median of 6 measured turns, bounded by `BACKGROUND_EXIT_WAIT`). Measured on Claude Code CLI 2.1.325 (2026-11-17), 6 one-line Haiku turns with stdin closed: the CLI exited 550, 575, 585, 970, 1,216 and 1,917 ms after its `result` line. A second run drove it the way PandaCode does (stream-json input with `--replay-user-messages`, a stdio MCP server attached, stdin closed at `result`, `bypassPermissions`), 12 Haiku turns: 6 tool turns (Read, Grep, Bash), 2 that started `nohup sleep 30 &` and 4 chat-only. Median 660 ms, max 1,374 ms; every CLI exited on its own within 3 s, and the background command did not keep it running (657 and 731 ms). A third run (2026-11-24, `scripts/agent-bench/warm-spare-bench.mjs`, results in `scripts/agent-bench/results/warm-spare-2.1.325.json`) drove Claude Code 2.1.325 on macOS arm64 with PandaCode's stream-json flags (`--input-format stream-json --output-format stream-json --replay-user-messages`), `--model sonnet`, bypass mode, a loopback Streamable HTTP MCP server listing `pandacode_explore`, `pandacode_track_files` and `pandacode_title`, and the full 6,325 B lead app instructions (unlike a real persisted turn, every suite passes `--no-session-persistence` and omits `--permission-prompt-tool stdio` and `--include-hook-events`, so a real turn's transcript flush at exit is not included in the ~12 ms telemetry-off exit), against a loopback Messages API stub (dummy key, no tokens, no cost): 24 one-line turns per suite (12 cold, 12 warm) in eight suites, 192 in all, every one exiting on its own with code 0 within 3 s. In PandaCode's default launch environment for plain Claude (the CLI's non-essential traffic on), the CLI exited a median 519.7 ms after `result` (max 530.4 ms) with a minimal config and 517.5 ms (max 534.6 ms) with the machine's user config, in line with the live Haiku runs above. With PandaCode's "Turn off agent telemetry" environment (`ENVIRONMENT` in `providers/privacy.rs`, nothing else changed) it exited after 11.5 ms (max 14.0 ms) and 12.0 ms (max 14.3 ms); with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` instead, 11.5 ms (max 15.4 ms) and 12.3 ms (max 14.8 ms). Resumed (`--resume=<id>`) launches matched: 517.5 ms (max 528.6 ms) in the default env and 10.7 ms (max 15.1 ms) with the telemetry switch. So about 0.5 s of an exit is the CLI finishing telemetry and related non-essential traffic, not the HTTP MCP host or the instructions, and PandaCode's telemetry switch removes it as fully as the non-essential-traffic switch. Not covered: approval handshakes, live Sonnet or Opus API turns, and Windows.
  - **Who waits for the exit**
    - A launch on the same conversation (`await_exit`, hurrying), at most as long as before the background reap: the natural exit, or SIGTERM at `EXIT_WAIT` (1 s after the run ended) plus `TERM_WAIT`, so 1.5 s in the worst case, below the 10 s cap. Back-to-back turns therefore gain little. This covers the queue's next launch. A Stop sent during that wait ends the launch at once.
    - Turn checks (`checks::turn_report_after_exit`, called by `run_turn_checks` in `lib.rs`; patient, so a check never cuts the natural exit), so a check never runs beside a dev server or watcher the CLI left in its group. If the exit cannot be confirmed the check is skipped (`checked: false` with the reason).
    - `providers::quiesce(session_id)`, which discards the task's warm spare and then awaits every process of the session. Callers: the harness console on a resumed task (`start_harness_terminal`), worktree removal, task deletion, and bot reset and delete. Worktree merge (`merge_worktree`) awaits the session's exit with `await_exit` (no spare to discard); both go through `guard_idle` in `lib.rs`: refuse while an agent runs, wait, refuse again if one started.
    - Quit sends Stop through `RunningAgent::send`, which marks the run stopped, so a launch cut short during its exit wait is not recorded as a clean turn. Then `providers::await_all_exits(QUIT_EXIT_WAIT)` runs before `providers::shutdown_all()`, and whatever is still alive is killed. `QUIT_EXIT_WAIT` is `BACKGROUND_EXIT_WAIT` + `TERM_WAIT` + 500 ms = 4 s, a cap for one exit, not for a chain: the flushing reap is first in its session's chain and gets its full budget, while a retire queued behind it may be cut by the cap and is then killed by `shutdown_all`. Once quitting begins, no new spare starts.
    - Turn-end change capture (`tracker.finish()` → `boundary()`) only compares snapshots already taken, so running it before the group kill reads no files.
    - `spawn_exit` registers nothing outside a tokio runtime, but every `warm::discard`/`retire` caller runs in an async context (for example `architect_control`), so the killed spare is always registered for a later `await_exit`.
  - **Limits**
    - A launch proceeds only on a confirmed exit. After 10 s (`EXIT_HARD_CAP`) it fails with a "still shutting down" error and the run ends as failed; the message stays in the transcript, and the queue holds until Resume.
    - Worktree removal (`remove_worktree`) refuses a running agent, quiesces, then re-checks that none started meanwhile.
    - Task deletion (`delete_session`) refuses a busy task (`refuse_if_busy`), quiesces the task and every worker it deletes, then `delete_state` re-checks busy under the agents lock; it does not quiesce again. `quiesce_all` waits for all those ids concurrently, tries every id and returns the first error.
    - Bot reset and delete (`quiesce_threads` in `bots.rs`) stop the gateway, then quiesce each conversation, all at once. A failure is logged and the reset or delete goes on; there is no re-check afterwards. Delete also stops the bot's channels; reset leaves them running, so a channel message arriving during a reset can still start a conversation.
    - Not covered by tests: a real 10 s exit stall, lead-spare adoption rates in real use.
- **Warm spares** (`providers/warm.rs`): after a successful plain-Claude turn the next turn's process starts in the background (2 ordinary spares, 10 idle minutes; managed workers, cloud runs, GLM, MiMo and Alibaba Token Plan get none, see below). A follow-up adopts one only when model, mode, effort, Fast Mode (`fastMode`), folder, resume ID, instructions, tool catalog, worker trim and the on-disk Claude Code startup config all match (`warm::key_with`; the MCP server is rebound to the new turn at the same address), so it skips the CLI's startup; anything else starts cold. The `claudeConfig` fingerprint stamps file metadata only. From `cwd` through the nearest `.git` repository root, it stamps `.mcp.json`, `.claude/settings.json`, `.claude/settings.local.json`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `.claude/CLAUDE.md`. It also walks `.claude/rules`, `.claude/agents`, `.claude/commands` and `.claude/skills` to depth 3 with at most 128 entries per folder, following symlinked folders once without looping. In ancestors above the repository root, it stamps `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `.claude/CLAUDE.md` and applies the same walk to `.claude/rules`. In a linked worktree's main checkout, it stamps only `.claude/settings.local.json`: committed `.claude/` files come from the worktree's own checkout, and Claude Code does not load the main checkout's root `AGENTS.md` or `CLAUDE.md` into the worktree (matching `claude_policy.rs`). In the effective Claude config folder, it stamps `settings.json`, `settings.local.json` and `CLAUDE.md` and applies the same bounded, loop-safe walks to `rules`, `agents`, `commands` and `skills`. Folder resolution uses the same rules as launch (`resolve_claude_config_dir_env`): the task's named Claude connection's `CLAUDE_CONFIG_DIR` / `config_dir`, then the saved provider environment's `CLAUDE_CONFIG_DIR`, then the inherited process `CLAUDE_CONFIG_DIR`, then `<home>/.claude`. It resolves paths literally without shell `~` expansion and matches `CLAUDE_CONFIG_DIR` case-insensitively on Windows; an explicit empty `CLAUDE_CONFIG_DIR` does not fall back to `<home>/.claude` for policy resolution, and the warm key marks it distinctly from unset and stamps user files and folders under both `<cwd>` (where Claude Code resolves an empty `CLAUDE_CONFIG_DIR`) and `<home>/.claude`, so edits in either place invalidate idle spares. When home cannot be resolved, or a legacy named connection stores `HOME`, `USERPROFILE` or `CLAUDE_CONFIG_DIR` as a secret variable, the launch has no warm key (`warm::key` returns `None`), so no spare is started or adopted; the connection form rejects `HOME`, `USERPROFILE` and the harness's config-folder variable as secrets. When `CLAUDE_CONFIG_DIR` points elsewhere, it also stamps `~/.claude/CLAUDE.md` and walks `~/.claude/rules`. The fingerprint includes host `managed-settings.json` and `managed-settings.d`, including under Windows `C:\Program Files\ClaudeCode` and legacy `%PROGRAMDATA%\ClaudeCode`. The key also stamps the launch's effective binary (the task's named connection `executable` when set, otherwise the resolved global Claude CLI binary) with its symlink target and file metadata, and PandaCode's in-app updater (`update_agent`) discards pooled spares at once when it updates Claude. Colab sign-in, disconnect and option saves that change `nativeTools` or `colabMcp` also discard pooled spares (`cloud/colab/settings.rs`; `accelerator` and `highMem` saves do not), and Colab tool availability is part of `launch_host::launch_inputs`, so a lead-spare renewal sees it. A cold launch with no pooled spare skips the config fingerprint walk. A change in stamped metadata makes the next turn start cold. A spare can retain older state for `~/.claude.json` (Claude Code rewrites it on every startup, so the fingerprint excludes the user- and local-scope MCP servers that `claude mcp add` writes there), Windows registry managed policies, files past the walk's depth or entry cap, `@`-imported or plugin files outside the stamped paths, and what hooks produce at run time. Launch numbers come from one app-wide counter (`NEXT_LAUNCH`), `warm::discard` also forgets the task's launch number (a spare still starting for the old launch is dropped), and every spare removal (a missed take, expiry, a refused registration, eviction, replacement by a newer spare for the same task, `warm::discard`, retiring spares whose worktree/folder is removed or recreated, and a launch that takes no spare) goes through one path (`warm::retire` → `exit::spawn_exit`): the process is killed outside the pool lock and its exit is registered under the task, so the next same-session launch (`await_exit`) waits for it, as it does for a finished turn's reaper. Outside a runtime nothing can wait; dropping still kills it.
- **Maintenance turns** (`/compact`, `/status`, `/context`, `/usage`, `/cost`, `/mcp`, `/tasks`, `/help`; `Resolution::maintenance`) keep the bare command as their message but carry the cached instructions, which are part of the warm key, so they adopt the task's spare instead of killing it (`a_maintenance_turn_matches_the_good_spare_and_only_compact_withholds_the_next`). The read-only commands (`/status`, `/context`, `/usage`, `/cost`, `/mcp`, `/tasks`, `/help`) keep warming a spare after they finish. Only `/compact` withholds the post-turn spare (`lead_spare::starts_spare`), so the next real turn after a compaction starts cold once: a spare started after `/compact` would hold the pre-compaction conversation. A compaction stays due across a maintenance turn, and the next real turn answers it.
- **Warm spare switch (on by default).** Settings → Agents → **Warm Claude spares**
  controls both pools. Off writes the empty `warm-spares-off` marker in app data;
  an unreadable marker also means off. Turning it off (`disable_all`) immediately
  retires pooled ordinary and lead spares and invalidates in-flight starts and pending renewals.
  No spare is adopted, started or renewed while it is off. Spares hold idle Claude
  Code processes (~195–255 MiB RSS each on short sessions, up to 4; measured on
  Claude Code 2.1.325, macOS arm64, after 2–3.5 s of idling, from the resumed
  one-turn medians (195.6 MiB with the telemetry switch, 204.6 MiB default; the
  50-turn probe 194.7–205.3 MiB) through fresh minimal and full user config
  (251.8 MiB), see What a spare costs and saves; RSS after up to 10 idle minutes
  is unmeasured, and long resumed histories, plugins or extra MCP servers can use
  more) and run `SessionStart` hooks ahead of the next turn, while an unused spare
  is retired with `SIGKILL` and never runs `SessionEnd` hooks; disable them to
  avoid that idle memory, early hook execution and unpaired `SessionStart` hooks. `disable_all` also bumps
  `discard_epoch` and clears the lead `gone` notes so later wakes log nothing. A
  Claude CLI update or a Colab settings change instead calls `discard_all`, which
  retires the pooled spares but keeps `discard_epoch` and the lead `gone` notes, so
  the next wake still reports why its spare went away.
  - **Trade-off with "Turn off agent telemetry".** That switch alone removes
    ~1.5 s of every cold Claude start (cold median 1,758 → 261 ms on a minimal
    config) and ~0.5 s of the post-`result` exit (520 → 12 ms), for every turn,
    spare or not. With it on, a warm spare saves only ~0.22–0.25 s per adoption
    (0.17 s on a resumed one-turn session), still for ~195–255 MiB of idle RSS
    per spare (the switch is not consistently lower RSS, see below) and `SessionStart` hooks run early. Whether that is worth it
    depends on how often follow-ups land within the 10 idle minutes, which is
    unmeasured (see the current-launch totals below).
- **Git state (`gitHead`, `warm/key.rs`).** The warm key stamps `<gitdir>/HEAD` and the ref it points to (in plain repositories and in linked worktrees, whose shared refs it finds through `commondir`). It finds the git folders through the same `claude_roots::git_dirs_for` that policy resolution uses (pointer files read up to 16 KiB, `config` up to 1 MiB, `\` line continuations and a bounded local `[include]` honored; `[includeIf]` and an unreadable or unknown common dir fail closed, so the launch has no warm key rather than a wrong one). It stamps `packed-refs` only when the ref has no loose file, so a `git gc` or `fetch --prune` that rewrites `packed-refs` does not make a spurious miss, and on reftable repositories it stamps `reftable/tables.list` instead. It intentionally leaves out `.git/index`, so switching branches or committing between turns starts cold (`changed: gitHead`), while uncommitted working-tree edits still adopt an ordinary spare. That spare's initial `gitStatus` reminder can then be up to 10 minutes old, until the agent checks git itself or a branch switch or commit invalidates the spare. Lead spares also check working-tree status (see Lead spares below).
- **Idle and renewal bounds use both clocks.** The 10-minute idle limit and the 30-minute bound on a lead renewal chain are each checked against `Instant` (monotonic) and `SystemTime` (wall clock), and a spare past either is not adopted. `Instant` can stop advancing while a laptop sleeps, so without the wall-clock check a spare could come back adoptable hours later with hours-old hook output and `gitStatus`.
- **Checkout guard (`checkout_busy.rs`).** Worktree merge and removal refuse while an agent runs or a background exit is pending in the checkout, including agents in its subfolders. A path inside a nested linked git worktree (a `.git` file whose git dir has a `commondir`, such as `root/.claude/worktrees/...`) belongs to that worktree, not `root`; submodules and vendored nested repositories have no `commondir` and stay guarded as part of `root`. `in_nested_checkout` resolves `..` segments before walking ancestors, so a path such as `root/.claude/worktrees/x/..` still marks `root` busy.
- **Concurrent starts.** Each pool also caps the spares still starting (`Spares::starting`) at its own limit (`LIMIT` 2 ordinary, `LEAD_LIMIT` 2 lead), so a burst of turns finishing together does not spawn unbounded processes. The cap bounds concurrency, not churn: sequential turns across more than 2 active ordinary threads still replace each other, the newest spare evicting the oldest idle one, which shows in `evicted` in the totals.
- **Churn and expiry backoff (`PoolChurn`).** When a pool evicts `limit` spares in a row with no adoption in between (for example round-robin turns across 3 or more threads), it stops starting new spares for a 5-minute cooldown. When 3 spares in a row expire unused in a pool with no adoption between (`EXPIRY_BACKOFF_STREAK` 3), starts in that pool pause for 30 minutes (`EXPIRY_COOLDOWN`), so a user who rarely follows up within 10 minutes stops paying idle memory and early hook runs for nothing. On a lead pool a whole unadopted renewal chain counts as one unused expiry, recorded only when the chain ends without renewal, without a wake superseding it, and with spares on, so renewals within a chain never trigger the 30-minute pause mid-chain; expiries while `warm-spares-off` is set never count toward the backoff. A third rule covers launch-time misses: 3 consecutive `not used` misses in a pool with no adoption between (`MISS_BACKOFF_STREAK` 3) pause starts in that pool for 5 minutes (`CHURN_COOLDOWN`), the same as eviction churn. Any committed adoption resets all three streaks and ends a pause at once; otherwise a pause ends when its cooldown lapses. Starts skipped this way are counted in `churn_skipped` (shown as `paused` in Settings → Agents), so the idle memory and early hook runs that churn would waste stay visible instead.
- **Lead spares** (the pool, its constants and the renewal loop are in `providers/warm.rs`; `src-tauri/src/lead_spare.rs` decides whether to keep and renew):
  - A team lead whose turn ends with live workers keeps its spare in a separate pool (`LEAD_LIMIT` 2) that ordinary tasks never evict.
  - **Working-tree freshness.** Every team works in the lead's shared checkout (`architect.rs` accepts only `workspace == "shared"`), so lead spares serve teams whose live workers are all read-only (such as Council reviews or read-only research swarms). A team with any live write worker starts no lead spare: its edits change the shared checkout and would leave the spare's initial `gitStatus` stale, so the spare would cost memory and hook runs for nothing. An all-read-only team's lead spare stamps a SHA-256 digest of bounded `git --no-optional-locks status --porcelain=v1 -z --untracked-files=normal` output (run through `workspace::run_git_bounded`, `GIT_STATUS_TIMEOUT` 500 ms, 1 MiB cap; measured on this 2,326-file repo with `core.fsmonitor=false` across 10 runs after warm-up: median 46.3 ms, max 71.2 ms) read after `await_exit_patiently`, right before the spare spawns, so it matches the `gitStatus` snapshot Claude Code takes at spawn, and compares it again at adoption. The status runs concurrently with the warm-key config walk (`tokio::join!`), so a slow repository costs at most 500 ms instead of stalling adoption. That bound is not free: with **Turn off agent telemetry** on, where an adopted spare saves only ~0.17–0.25 s, adopting a lead spare in a slow repository whose `git status` takes 250–500 ms can be slower than starting cold (on this repository the 46.3 ms median is well inside the saving). A changed working tree starts the wake cold (`changed: gitStatus`) instead of adopting stale status, and an unreadable or timed-out status fails closed (`its git status cannot be read`).
  - On expiry it is restarted at most `MAX_RENEWALS` (2) times; the check is asked once per expiry and holds only while every live worker still runs and none waits on the user, and never once the lead's wake has launched (a "no" ends the chain).
  - A renewal re-reads the settings read at spawn (login, environment, telemetry, named connection) and the launch inputs (`warm::still_current`), so a stale one is not restarted. That check leaves out `gitStatus`: a renewal reads `git status` fresh right before it spawns. With `warm-spares-off` present a renewal ends silently, without logging `not renewed: its launch settings changed`.
  - A brief's roster delta is recorded as seen only after its run ends cleanly (`coordination::brief_accepted`).
  - `stop_session` and the team's Pause or Stop (`architect_control`) drop it (`warm::discard`), and a lead turn ending while its team is paused, stopped or unreadable keeps no spare (`lead_spare::pool` → `Drop`).
  - A team that ended by itself (completed, ready, failed) gives its lead an ordinary spare with no renewals.
  - Tests: `cargo test --lib lead_spare` and `cargo test --lib warm`.

Lead spares since launch: ...` when its renewal check finds the launch settings changed, without counting the expiry a second time); a refused registration (`spawn::register`: a spare that finished spawning after its task's launch epoch moved) is counted in both `started` and `discarded`, keeping the ordinary identity exact, and logs `Warm Claude agent discarded. Ordinary spares since launch: ...` (or the lead line) with the running totals; and turning the switch off (`disable_all`) or a CLI update or Colab settings change (`discard_all`) logs `Warm Claude agent discarded. Ordinary spares since launch: ...` / `Team lead's warm Claude agent discarded. Lead spares since launch: ...` when it retires pooled spares.
    - `Warm Claude agent not pooled; starting cold.` and `cold launches without a spare` cover only supported non-worker follow-up turns (a `resume_id` is present) while **Warm Claude spares** is on, that found neither a pooled spare nor a lead `gone` note. Managed workers never get spares and are excluded; with spares off a launch logs and counts nothing (`disable_all` also clears the pending lead `gone` notes, so after switching off neither an ordinary nor a lead launch logs or counts anything); and a brand-new conversation's first turn, which can never have a spare, is excluded.
    - A lead wake is attributed to the lead pool when its spare or its removal reason (the pool's `gone` table) is present. A lead wake that launches cold with no spare (one that never started, was declined or skipped by the shared-checkout rule above, or whose removal reason aged out of the 64-entry `gone` table) is counted in the lead pool's own totals, not the ordinary `cold launches without a spare` counter.
    - `adopted` is counted only once `Adopting::into_parts` commits the spare to the launch; a taken spare whose rebind fails or whose launch aborts before then counts as `not used`.
    - `not used` means different things per pool. On the ordinary pool it counts only launch-time misses on a still-pooled spare, so `started` = `adopted` + `not used` + `expired` + `evicted` + `replaced` + `discarded` (once every started spare has left the pool). On the lead pool it counts every lead wake that missed its spare, including wakes whose spare was already counted in `expired`, `evicted`, `replaced` or `discarded` when it was removed, so lead `not used` overlaps with those removal counters.
  - The totals are separate in-memory counters per pool, reset on restart and never saved or sent anywhere. Because they count every spare `started` and every one that `expired`, was `evicted`, `replaced` or `discarded` next to `adopted` and `not used` (and, for each pool, `cold launches without a spare`), spares that were started but never used stay visible instead of hidden behind the adoption count. Settings → Agents shows the current-launch totals beside the **Warm Claude spares** switch (the `warm_spare_stats` command, read locally when the page opens and when the switch is toggled, not streamed), showing ordinary `<adopted>/<started> adopted` plus `not used`, `expired`, `evicted`, `replaced`, `discarded`, `cold` and `paused` (starts skipped by backoff; each count shown whenever nonzero), with the lead totals kept separate after ` · lead ` in the same form, so lead misses are never added to ordinary misses and unused expiries and the adoption rate are never hidden; a desktop app opened from the Dock or Finder can see its real adoption rate too. The stderr lines carry the same totals (take the last line of each kind; `pandacode serve` prints them to the terminal, the desktop app only when started from a terminal), and their per-line reasons say why each miss started cold. The `expired idle (not renewed: ...)` line at an expiry is not counted as a miss: the expiry is counted once in `expired`, and the wake that follows counts its miss as `it expired`. How often either kind of spare is adopted in real use has not been measured yet.
  - A changed reasoning effort is a warm-key field, so it discards the lead's spare (`changed: effort`) and the next wake starts cold.

### Pre-registration: batch S2

Written on 2026-11-07, after one smoke (`rep-explain-queue`, seed 99, both arms, $0.42, runs in `runs/smoke-S2`, never analysed with S2) and before any S2 run.

**Question.** For read-only team workers, does the worker tool trim lower billed cost, with localization and report quality unchanged?

**Arms.** Both use the S1v3 worker setup: Claude Code 2.1.317, worker model `sonnet` pinned to `claude-sonnet-5-5`, the `after` harness flags with the explore snapshot `bin-f`, `LOOK` appended, and the message `<report sentence>\n\n<task prompt>` with no saver block. They differ only in one flag. Both lists are read from `providers.rs` at run time, and their sha256 is pinned in `batch.json`.
- `BASE`: `--disallowedTools=ScheduleWakeup,Monitor,CronCreate`, the app's launch for every task before this change.
- `LEAN`: `--disallowedTools=` the session-bound, worker and read-only lists, which is `claude_disallowed_tools(Some(true))`.

**Tasks** (`scripts/agent-bench/tasks-s2.json`): S1's 20 localization tasks and 8 report tasks from `tasks-saver.json`, graded as in S1v3. No edit tasks, because LEAN is the read-only trim.

**Seeds.** 1, 2 and 3 for each arm: 168 runs. The job order and the arm order come from the batch seed in `batch.json`.

**Primary.** Billed cost per run, `BASE` → `LEAN`. We use per-task means over seeds, a two-sided Wilcoxon signed-rank test on the per-task differences, and a 95% bootstrap CI of the mean per-task relative change. Cost is read as lower only if p < 0.05 and the CI excludes 0.

**Secondary,** Holm-adjusted together:
- first-step cache-write tokens;
- input, cache-read and cache-write tokens.

Output tokens, steps and wall time are descriptive.

**Quality,** descriptive with no gate: localization recall and precision, and report rubric recall. Each is given as the mean per-task difference with a 95% bootstrap CI.

**Exclusions.** We exclude only runs whose `init.model` is not the pinned model. A run that errors or times out keeps its tokens and its grade.

**Expectation, written down before running:** a 2–4% cost drop. With 28 tasks it may not reach significance.

**Cost.** About $27 at $0.16 a run. The user approved unlimited spend.
